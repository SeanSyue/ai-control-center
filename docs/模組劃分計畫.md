# 依功能劃分模組：一扇大門，複雜藏在門後

> **歷史文件，非目前承諾（2026-09-25 整理）。** 保留當時的設計討論、測量與用語，可能包含過時狀態；目前功能、成功使用陳述、已知問題與維護政策請依[文件導覽](README.md)閱讀。「老闆／使用者」指單人作者與 AI 協作時的角色，不代表另一個開發團隊。

老闆 2026-08-23 的話：

> 我們需要依照功能去劃分模組，未來有任何需求只需主程式對應單一大門，
> 對應功能需求的時候只要去找這個對應模組就好，**所有邏輯藏在門後**。

那正是《AI 協作手冊》第二節「深模組」那一條：

> **一扇簡單的大門，複雜藏在後面。**
> 判斷方法是**刪除測試**：想像把這個模組拔掉——天下大亂就是好模組，
> 程式碼反而變清爽就是空殼。
>
> **不照做**：AI 的視野有限。邏輯散在五個檔案裡，它為了看懂整個流程要瘋狂
> 跳轉，超過記憶範圍就開始瞎猜，最後把原本正常的程式也一起改壞。

## 現在的形狀（2026-08-23 量的）

| 檔案 | 行數 | 它負責幾件事 |
|---|---|---|
| `app/core/orchestrator.py` | 2,370 | 提示詞組裝、派工、成品落地、共同記憶、對話 id、時間軸、驗證宣告 |
| `app/core/workflow_worker.py` | 1,871 | **十一件**（見下）|

`workflow_worker` 一個檔案裡有：需求確認、擬做法、先交做法、執行、討論、
駁回驗收標準、驗證、複查、修正迴圈、核准、拍板判定，再加十幾種結局的組裝。

**它不是深模組，它是一條很長的走廊。**大門很小（`run()`），但門後沒有房間
——每一件事都攤在同一層地板上，而它們互相看得到彼此的區域變數。

### 這件事今天就在收成本

今天加「先交做法」那一步的時候，**一百多處假腳本的位置全部位移一格**。
那不是測試寫得不好，那是「所有步驟共用同一條時間線」的必然結果：
沒有房間，就沒有門可以敲，只能數第幾個。

（那一輪的解法是讓假 CLI **照內容**回答前置步驟，不再靠位置——那已經是
在補這個結構問題了。）

## 要切成哪幾個模組

一個功能一扇門。每一扇門的簽章長得一樣：

```
<動詞>(現場, ...) -> (產出, 要不要停下來)
```

（**大門不叫 `run`**：那是安全檢查認得的啟動器名字——它掃 `.run(` 有沒有拿
變數當指令，叫 `run` 會被讀成「這個檔案開始動態組指令了」。那條檢查沒有錯，
是命名踩到它，而為了命名去放寬一條安全檢查是最糟的交換。）

`workflow_worker` 退化成一個**只會按順序敲門**的東西。

| 模組 | 大門 | 藏在門後的 |
|---|---|---|
| **需求確認** | `Intake.run()` | 問答輪、格式剖析、沒有輪數上限、標準落地、專案計畫書、蓋章 |
| **擬做法** | `Planning.run()` | 每一格 plan、看得到前一格、討論、對標準提異議 |
| **執行** | `Building.run()` | 先交做法、派工、討論、駁回標準、重訂之後重來 |
| **驗證** | `Verification.run()` | 專案宣告的指令、怎樣算過、逾時、沒宣告 |
| **複查** | `Reviewing.run()` | 每一格複查、異議兩級、指名駁回、修正迴圈 |
| **核准** | `Approval.run()` | 章的敘述、有紅章不派、拍板或退回 |
| **討論** | `Consulting.ask()` | 指名、名冊、不准問自己、同一題兩次就是卡住 |
| **章** | `Chain` | **已經是深模組了**（`approval_chain` ＋ `run_stamps`）——可以當範本 |

### 為什麼「章」已經是對的形狀

外面看到的只有四件事：`add()`、`live()`、`readiness()`、`describe_*()`。
而門後藏著：版本兩條線、依賴失效、後蓋的蓋掉先蓋的、機器章與審查章的差別、
五種判定的優先順序。

**把它拔掉會天下大亂**——那就是深模組測試的通過條件。

## 進度（2026-08-23）：**九扇全部搬完**

`app/core/workflow_worker.py` **1,871 → 1,470 行**。行為零變動。
門後總共 1,114 行，分在七個檔案裡——每一個都只回答一件事。

| # | 門 | 大門 | 狀態 |
|---|---|---|---|
| M1 | 需求確認 | `intake.confirm(site)` | ✅ |
| M2 | 擬做法 | `planning.draft(site, criteria)` | ✅ |
| M3 | 執行 | `building.build(site, work_plan)` | ✅ |
| M4 | 驗證 | `verification.declared(site)` / `check(site)` | ✅ |
| M5 | 複查 | `reviewing.look(site, ...)` | ✅ |
| M6 | 核准 | `approval.decide(site, ...)` / `is_undecidable(...)` | ✅ |
| M7 | 討論 | `consulting.ask(site, role, send)` | ✅ |
| M8 | 章 | `Chain` | ✅ 本來就是對的形狀 |
| M9 | 收場 | `outcomes.describe(result)` | ✅ |

### 為什麼 M7 排到 M2 前面

**M2 依賴 M7。**擬做法那一格在派工的時候可以說「我要問某某」，所以
`planning.draft` 一定會呼叫討論那條路——而討論那條路如果還在回**結果字典**，
擬做法這扇門就得認識那個字典，那正是這批門要消滅的東西。

順序照依賴走，不照編號走。清單上的編號是主題編號，不是施工順序。

### M9 不在原本的清單裡，為什麼還是做了

它是頁面設計那一輪查出來的**同一種病**：收場長什麼樣的知識散在四個畫面，
而 `main_window` 那條判定鏈最後掛了一個 `else` 兜底。

> **深模組的判斷方法是刪除測試**：把它拔掉會不會天下大亂。
> 把 `outcomes.py` 拔掉，四個畫面都不知道一次執行是怎麼收場的。

它也示範了這批門要長成什麼樣：

- **大門一扇**：`describe(result) -> Outcome`
- **門後藏著**：二十幾種收場、五組分法、`NOT_DECIDABLE` 底下六種判定、
  「結果裡有更具體的說明就用具體的」
- **沒有預設值**：不認識的丟例外。這一條是 M2–M7 也要照抄的——
  **有預設值的分類等於沒有分類**

## 什麼時候做

**~~不要在老闆那次五節點測試之前做。~~**（2026-08-23 老闆推翻：
「深模組一定要在五節點測試前做完」。下面那段理由留著，因為它講的風險是真的
——處置改成「一次一扇門，每一扇搬完跑完整測試＋負向驗證」，不是「延後」。）

理由：這是一次會動到引擎每一條路的重構。它做壞的時候，症狀跟「五節點流程
本身有問題」長得一模一樣——而那正是那次測試要回答的問題。**兩件事混在一起，
那次測試就白跑了。**

順序：

1. 五節點測試跑過一次（拿到基準線）
2. 一次搬一扇門，每一扇搬完跑一次完整測試 ＋ 負向驗證
3. 全部搬完再跑一次五節點，跟基準線比

### 搬的時候的硬條件

- **一次一扇門。**一次搬兩個的話，紅燈出現時分不出是哪一個造成的。
- **不准順便改行為。**搬家就是搬家；行為要改的話另外一次。
- **每一扇門搬完，`tools/negative_control.py --all` 要全紅。**配方比的是字串，
  搬家一定會讓一批配方腐爛——**那些要照現行程式碼更新，不准刪掉**。
- 搬完之後 `workflow_worker` 應該只剩「按順序敲門」與「把結果組成一份回報」。
  它如果還在做判斷，那就是門開得不夠大。

## 搬完之後學到的三件（2026-08-23）

### 一、順序照依賴走，不照編號走

M2（擬做法）會呼叫討論那條路。討論那條路如果還在回**結果字典**，
擬做法這扇門就得認識那個字典——那正是這批門要消滅的東西。所以 M7 先搬。

### 二、`Stop` 裝不下的那幾種，不要硬塞

四扇門回的不是 `Stop` 而是自己的小型別：

| 門 | 回什麼 | 為什麼不是 `Stop` |
|---|---|---|
| 驗證 | `Checked` | 三種結果不是兩種（過／沒宣告／逾時），而且逾時那份回報要帶測試結果 |
| 複查 | `Reviewed` | 回報要帶 claude 結果、測試結果、codex 結果三個 |
| 核准 | `Undecidable` | 同上 |
| 執行 | `Built` | 還要帶「哪幾格真的動了手」（給蓋章用）|

共同點：**這一輪真的跑完了，那些結果要照原樣帶進回報**——而那份回報有
十九個欄位，門後的模組不該認識它。硬塞進 `Stop` 的話，`Stop` 會慢慢長成
第二份結果字典。

### 三、搬家會讓一批負向驗證安靜地失效

這一輪總共有 **27 條配方**因為程式搬家而比不到目標字串。它們**不是紅燈也
不是綠燈——是那條檢查不存在了**，而 `--check` 印出來之前沒有任何跡象。

同一件事在測試裡也發生了一次：「缺章要擋」那條測試換掉的是
`workflow_worker.requires_for`，也就是**呼叫端**。程式一搬家，它會安靜地
什麼都沒換到而測試照樣是綠的。已經改成換掉定義它的模組。

> **換東西要換定義它的地方，不是換用它的地方。**
