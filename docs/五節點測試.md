# A. 這條線排出來長什麼樣〔跑出來的〕

```
發想     plan     codex     ← NODE1，而且它自動成為「訂驗收標準」的那一格
規劃     plan     claude    ← NODE2，核心
ui設計   plan     codex     ← NODE3
執行     work     claude    ← NODE4
審閱     approve  codex     ← NODE5
```

引擎算出**這一次該有哪些章**：

```
【發想】acceptance（review）   ← 驗收標準是誰訂的
【執行】work（machine）        ← 誰做的、跑出什麼
【engine】verify（machine）    ← 驗證指令的結果
【審閱】work（review）         ← 誰看過而且同意
```

**注意那份清單裡沒有「複查」。**它是從陣容算出來的，而這條線上沒有複查那一格
——所以簽核鏈根本沒要求那個章。

# B. 卡住的三件，兩件已經解決

## 1. ~~引擎硬性要求一定要有一格「複查」，否則整件事停~~ ✅ 2026-08-24 修掉

**這是 AICC 自己前後矛盾**：`requires_for(lineup)` 算出來的章沒有要求複查，
而執行迴圈硬性要求有那一格。簽核鏈說不需要，跑的迴圈說一定要。

停下來那一版的理由是「沒有複查就少一個章」——那句話在 `requires_for` 還是
**寫死**的年代是對的，改成從陣容算之後就不是了。

現在：跳過複查那一段往下走，**而且在時間軸留一筆**（不准安靜地跳過——
使用者不小心把複查那一格刪掉之後，他會得到一個「沒有人看過但看起來很正常」
的結果）。

# C. 那些「回頭的線」不是資料，是行為

他說「node 圖裡面可以有分支，還可以針對職位或角色的針對跳回去確認」。

**陣容的資料裡沒有邊。**那些線是跑的時候長出來的：

| 他寫的 | 引擎的哪一條路 |
|---|---|
| NODE1↔NODE2 確認可行性 | 討論（`consulting.ask`）——任何一格對任何一格，**沒有次數上限** |
| NODE3 有問題向 NODE2 討論 | 同上 |
| NODE4 有問題與 NODE3 討論 | 同上 |
| NODE2 依角色分發回負責 NODE | 駁回**指名一格**（`parse_review` 的 target／`parse_approval` 的 who）|
| 下面的人有事找 NODE2 | 討論——**NODE2 是核心，因為它是寫企畫書的人** |

所以**畫面不用畫回頭的箭頭，也不該畫**：那條線不是排出來的。

衝突只發生在**沒有排核准那一格**的陣容。

| | |
|---|---|
| 2026-08-22 拍板 | 沒有核准那一格的陣容**完全不跑這一步，一次呼叫都不多**；出廠的一人與兩人表格「成本一毛都不該變」。有測試在守 |
| 2026-08-24 他說 | **規定**最後一個 NODE 去驗證 |

兩條同時成立不了。照 08-24 那條做，出廠兩格的陣容每一次執行都會多一次唯讀
呼叫。

**做法已經寫好，等他點頭就是三行**：

```python
def chain_checker(lineup) -> str:
    """驗簽章的那一格。最後一格，除非有人被明確排成核准。"""
    approvers = [s.role for s in lineup if s.duty == DUTY_APPROVE]
    if approvers:
        return approvers[-1]
    slots = list(lineup)
    return slots[-1].role if slots else ""
```

**為什麼這一格可以自動指定、而「執行」那一格不行**：那兩種職責會給出**權限**
（訂標準的決定怎樣算做完、做事的拿到寫檔案的能力），使用者沒排就自己挑等於
發出一個他沒授權的權力。**驗簽章不給任何權限**——唯讀、不重做、推翻不了機器
章，說「可以」還得寫理由。多問一格，最壞情況是多一個意見。
