# Graph Engineering，以及 AICC 已經在哪一格

老闆 2026-08-25 丟了一支影片進來，同一則訊息裡問的是：

> 我想到那個如果我們有就是第二行分支的話，那是不是會沒辦法再匯入第一行的
> NODE？還是我們 NODE 現在這樣不讓使用者畫線像 N8N 那樣的話，
> **就完全可以按照職責指向來進行？**

**那兩件事是同一題。**這一份把影片的詞彙對到 AICC 的程式碼上——
**每一句關於 AICC 的話都附檔名行號**，因為這份文件唯一的價值就是
「別人講的概念」跟「我們手上真的有的東西」之間那條線畫在哪。

> ⚠️ 影片講的是**一般的做法**，不是 AICC 的規格。
> 兩者不一樣的地方，這一份會明著寫「**AICC 不是這樣，理由是⋯⋯**」。

---

# 一、五層概念，AICC 各在哪

影片的分法（Prompt → Context → Harness → Loop → Graph），
以及**每一層在這個 repo 的哪個檔案**：

| 層 | 影片說它管什麼 | AICC 的哪一份 |
|---|---|---|
| **Prompt** | 要做什麼、限制、成功標準、回傳格式 | `app/core/prompt_builder.py`、`app/core/prompt_text.py` |
| **Context** | 這一步**剛好夠**的資訊 | `app/core/rule_layers.py`（每種職責拿到哪幾層）、`app/services/project_knowledge.py`（八份共同記憶）|
| **Harness** | 能讀檔嗎、能跑程式嗎、有什麼權限 | `app/adapters/cli_runner.py`、`.aicc/project.json` 的敏感度與權限模式 |
| **Loop** | 做完檢查、不合格就修、再跑一次 | `app/core/workflow_worker.py` 的修正迴圈（`fix_attempts`）|
| **Graph** | 誰做什麼、資料怎麼交接、哪裡驗收 | `app/core/lineup.py` ＋ `app/core/steps/`（九扇門）|

影片那句「**這五個不是競爭關係**」在這個 repo 是字面上的真：
一次執行同時用到全部五層，而**修正迴圈就住在其中一格裡**。

# 二、三個零件：node、edge、state

## node ✅ 有，而且「node 不等於 agent」這條已經是定案

影片：

> Node 不等於 Agent。很多確定性的工作⋯⋯用傳統程式寫三行 code 就搞定了，
> 速度快，成本是零，而且百分之百精準。

AICC 一直是這樣：**驗證那一格跑的是一個指令，不是 AI**
（`.aicc/project.json` 的 `verify_command`，由
`app/services/project_verification.py` 讀）。而**人工審核本身也是一格**
——決策關卡停下來問使用者，那一停在 `app/core/steps/` 底下有自己的門。

2026-08-25 補進 `DECISIONS.md`。

## state ✅ 有，而且影片那句「state 不是聊天紀錄」正是這個專案在做的事

影片：

> 聊天紀錄就像是把所有文件、便利貼跟草稿一股腦全堆在同一張桌子上⋯⋯
> 但正式的 state 就像一張有標準欄位的表：**它有嚴格的讀寫規則，
> 可以隨時被存檔、版本比對，甚至在出錯時直接倒帶恢復。**

AICC 的 state 分三層，而**每一層都有嚴格的讀寫規則**：

| 在哪 | 存什麼 |
|---|---|
| `.aicc/runs/<run_id>/run.json` | 這一次執行怎麼收的 |
| `.aicc/runs/<run_id>/timeline.jsonl` | 過程 |
| **簽核鏈**（`app/services/approval_chain.py`）| **誰蓋了什麼章、蓋在哪一版內容上** |

那個「蓋在哪一版內容上」是影片沒有講到的一層：AICC 的章綁著
`content_digest`，**內容改了章就自動失效**。同一個形狀 2026-08-24 也用在
質化驗收的核准上（`app/services/qualitative_acceptance.py` 的 `Approval.digest`）。

## edge ⚠️ **有一條「架構線」，但它不是路由——這是 AICC 跟影片最大的差別**

> **2026-08-27 改寫。**這一節原本的第一句是「**AICC 的陣容資料裡一條邊都
> 沒有**」，而那句話從 2026-08-27 起是假的：`AgentSlot` 多了一欄 `parent`
> （「這一格接在哪一格後面」），為的是老闆 2026-08-22 那句
> 「有分支或沒分支無所謂，應該要是在一個方框內⋯⋯」——**框裡要畫得出連線。**
>
> **但下面那一整段「為什麼不畫線」一個字都沒有被推翻**，因為那一段講的是
> **路由**（誰可以問誰、駁回退給誰），而 `parent` 講的是**架構**（東西怎麼
> 流）。老闆自己把這兩件事分開過：「呈現的主要是專案架構，**沒有說不代表
> 不能跳著找對應人員詢問或討論**」。
>
> 落地成兩句話：`parent` **不進派工**——`slots` 的順序仍然是執行順序，
> 討論仍然是任何一格對任何一格，駁回仍然是指名。它今天唯一的讀者是畫面。
> 這兩件事哪一天要合併，是老闆的下一個決定，不是一個欄位偷偷做掉的事。

影片：

> Edge 就是節點之間的連線，它決定了資料怎麼傳遞、下一步該往哪裡走⋯⋯
> 交通、住宿和景點三個 node 就可以同時觸發，平行執行，
> **這也是由 edge 的路由規則來決定的**。

`AgentSlot`（`app/core/lineup.py:347`）今天有八個欄位：
`role`／`provider`／`session_id`／`credential`／`identity`／`duty`／
`writes_files`／`parent`。**只有最後那一個是邊，而它畫的是架構不是路由。**

那些「回頭的線」**是跑的時候長出來的行為**，不是排出來的資料
（`docs/五節點測試.md` §C 早就記過這件事）：

| 老闆畫的線 | 引擎實際怎麼走 |
|---|---|
| NODE1↔NODE2 確認可行性 | 討論（`app/core/steps/consulting.py:40`）——它拿到的是 `lineup.roles`，**全部座位**，任何一格對任何一格，**沒有次數上限** |
| NODE3 有問題找 NODE2 | 同上 |
| NODE2 依角色分發回去 | 駁回——**指名一格** |

### 為什麼不畫線（老闆 2026-08-25 拍板）

**畫線的路由會被忘掉，算出來的不會。**

N8N 那種做法，使用者少畫一條回頭的線，那條路就不存在了——
**而畫面上看不出來少了什麼**。職責指向是每一次重算的：

| 問題 | 誰回答 | 在哪 |
|---|---|---|
| 誰可以問誰 | **全部**，沒有限制 | `steps/consulting.py:54` |
| 誰做什麼 | `duty`（規劃／執行／複查／核准）| `lineup.py` |
| 誰驗整條鏈 | **最後一格**，除非有人被明確排成核准 | `lineup.py:230 chain_checker()` |
| 誰訂驗收標準 | **第一個不做事的節點**；整條線只有執行者的話**回空字串不硬挑** | `lineup.py:199 criteria_seat()` |

最後那一條的「不硬挑」值得看一次：硬挑一格的話，那一格會拿到
**訂驗收標準的權限**，而使用者從來沒有把它排成那個角色——
**而畫面上看不出來換過人**。

### 所以老闆那一題的答案

> 「第二行分支的話，是不是會沒辦法再匯入第一行的 NODE？」

**那個問題不會發生，因為沒有「行」。**每一格隨時看得到全部座位的名單，
要問誰就問誰。分支不是一種資料結構，是跑到那裡的時候的一個選擇。

# 三、影片講的三個痛點，AICC 各解到哪

## ① Context 污染與工具失焦 —— **解了**

影片：

> 如果你把訂房、地圖、搜尋、算數學、串 API 全塞給同一個 Agent，
> 它每走一步都要在十幾個工具裡猶豫不決。

AICC 的做法是 `app/core/rule_layers.py`：**每一種職責只拿到它該拿的那幾層**。
`tools/memory_budget.py` 每次改動都要跑，確認「該點名的都點到了」。

## ② 缺乏可觀測性與無法局部重跑 —— **解了一半**

影片：

> 每個 node 的輸入、輸出、路由選擇和驗收紀錄都會被清楚保留在 state 裡⋯⋯
> **然後只重跑住宿這個分支**。

AICC 有紀錄那一半（`tools/inspect_run.py` 讀得出每一格的問答與收場），
也有「哪裡出錯退回哪裡」（駁回會指名一格）。

**沒有的那一半是「只重跑那一格」**——`tools/inspect_run.py` 有
`--retry <第幾格>`，但那是人手動下的，不是引擎自己回頭。

## ③ 把做完當成做對 —— **這個專案這兩天都在修這一條**

影片：

> LLM 最大的盲點就是特別擅長完成表面任務⋯⋯
> **Graph 讓你在關鍵節點設立驗證機制**⋯⋯
> 雖然驗證器無法百分之百消滅所有幻覺，但它的價值在於
> **把原本藏在你腦袋裡的驗收標準明確寫成規則，由系統嚴格執行**。

這一段幾乎是 AICC 這兩天在做的事的說明書：

| 影片說的 | AICC 的哪一件 |
|---|---|
| 關鍵節點設驗證機制 | `verify_command` ＋ 質化驗收標準，**兩個都沒有的專案不准開始跑** |
| 把腦袋裡的驗收標準寫成規則 | `app/services/qualitative_acceptance.py`（維度＋案例＋反例）|
| 驗證器不能百分之百 | **所以 AICC 多了一層：簽核鏈**。章不齊就不准拍板 |

而 2026-08-24 掃出來的 30 條假綠燈，**每一條都是「做完了」跟「做對了」在
畫面上長得一樣**——影片那句話講的正是這個病，只是它沒有講到最刺的那一半：

> **一條壞掉的驗證器，跟一條好的驗證器，在報告上長得一模一樣。**

所以 AICC 在驗證器上面又加了一層：**負向驗證**
（`tools/negative_control.py`）——**綠燈在被弄紅過之前不算證據**。
那一層影片沒有提到，而它是這個專案最貴的一課。

# 四、影片說「先手動跑」，而那正是還沒發生的那件事

影片最後：

> 強烈建議你先從純手動版本開始跑起⋯⋯**先手動跑，才能看見這份工作到底
> 怎麼運作**。流程跑順後，再考慮把它自動化。

老闆的**五節點測試**就是這件事的反過來：AICC 已經自動化了，
而**那條線還沒有被一個真的人從頭走過一遍**。

他 2026-08-24 的原話：

> **五節點測試是我作為使用者的測試，不是你該跑的測試。**

影片那句「先手動跑才能看見它怎麼運作」，跟他那句是同一個判準。

# 五、這份文件**不改變任何已經拍板的東西**

影片是別人的說法，不是規格。這一份只做兩件事：

1. 把 AICC 已經有的東西對到一組通用詞彙上——以後跟外面的人講的時候，
   說「我們的 node 是⋯⋯」比說「我們的格是⋯⋯」省一輪。
2. 把**不一樣的地方**寫清楚，尤其是 edge 那一項——
   那是刻意的，而理由 2026-08-25 進了 `DECISIONS.md`。

影片自己也講了一句值得抄下來的：

> **絕對不是每一項任務都需要硬套 Graph。**如果是一次性的簡單任務，
> 一個 prompt 就能搞定的事，就千萬別硬把它拆成七個 node 自找麻煩。

那條對 AICC 是**產品定位**的問題，不是工程問題：一個只要一個 prompt
的任務，使用者不會打開 AICC。AICC 值得打開的門檻，
就是「這件事複雜到你想知道誰做了什麼、誰檢查過」。
